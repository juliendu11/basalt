# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

AdonisJS 6 (server) + Inertia.js + Vue 3 (SPA-style pages, SSR-capable) + Lucid ORM on MySQL/MariaDB + Tailwind CSS v4 + DaisyUI. Package manager entry points use Node's subpath imports (`#controllers/*`, `#models/*`, etc. — see `imports` in `package.json`), not relative paths.

## Commands

```bash
node ace serve --hmr      # dev server (also: npm run dev)
node ace build            # production build (also: npm run build)
node ace test             # run all tests (also: npm run test)
node ace test unit        # run one suite (unit | functional | browser)
node ace test --files="tests/functional/some.spec.ts"   # run a single test file
npm run lint              # eslint .
npm run typecheck         # tsc --noEmit + vue-tsc for inertia/
npm run format             # prettier --write .

node ace migration:run    # apply migrations, regenerates database/schema.ts
node ace migration:rollback
node ace make:controller / make:migration / make:validator ...  # standard Adonis scaffolding
```

Local infra (MariaDB, phpMyAdmin, Redis, Mailcatcher, push-notification-catcher) is defined in `docker-compose.dev.yml` — `docker compose -f docker-compose.dev.yml up -d`.

Test suites (`tests/unit`, `tests/functional`, `tests/browser`) are declared in `adonisrc.ts` but the directories don't exist yet — create them following that convention when adding the first tests.

## Architecture

This is a fairly bare AdonisJS starter (auth scaffolding is the only feature implemented so far: signup/login/logout, `home`, and error pages). The important, non-obvious parts of the setup:

### Generated code — do not hand-edit

Several files/directories are regenerated by tooling and are marked "DO NOT EDIT" or are gitignored build output:

- `database/schema.ts` — regenerated from migrations by `node ace migration:run`. Models compose against this (`class User extends compose(UserSchema, withAuthFinder(hash))`), so **add/change columns via a migration**, not by editing this file or the model directly. `database/schema_rules.ts` lets you customize how migrations map to the generated schema types.
- `.adonisjs/` — generated by the `adonisrc.ts` `hooks.init` pipeline (`indexEntities`, `indexPages`, Tuyau's `generateRegistry`) every time the app boots/dev-serves. This is what makes `#generated/controllers` (used in `start/routes.ts` as `controllers.NewAccount`) and `@generated/registry` (used by the Tuyau API client in `inertia/client.ts`) resolve. If routes or the Tuyau client seem out of sync with the latest controller/route changes, it's this index that's stale — restart the dev server rather than editing generated files.

### Request flow

- `start/kernel.ts` wires global and named middleware; `middleware.guest()` / `middleware.auth()` are the named ones used to gate route groups in `start/routes.ts`.
- `app/middleware/inertia_middleware.ts` overrides Adonis Inertia's `share()`/`flash()` to inject `user` (via `UserTransformer`) and validation `errors` into every Inertia page, plus a top-level `flash` prop (`flash.error` / `flash.success`) read on the client via `usePage().flash`. When adding new shared page data, extend this file rather than passing it per-controller.
- `providers/api_provider.ts` registers `ctx.serialize()` on `HttpContext` — a wrapper around a custom `ApiSerializer` that wraps API JSON responses as `{ data: ... }` and handles Lucid pagination metadata. Use `ctx.serialize(data)` (or `.withoutWrapping`) instead of hand-rolling response shapes for anything API-like.
- Transformers (`app/transformers/*_transformer.ts`, extending `BaseTransformer`) define the serialized/whitelisted shape of a model for both Inertia props and API responses — e.g. `UserTransformer` picks `id, fullName, email, createdAt, updatedAt, initials` and deliberately excludes `password`.
- Validators (`app/validators/*.ts`) use VineJS. Note the pattern in `signupValidator`: `passwordConfirmation` is declared explicitly (not just as a `.confirmed()` option) so its validation errors are visible to the frontend form.

### Frontend (Inertia + Vue)

- Pages live in `inertia/pages/**/*.vue` and are resolved by name (e.g. `inertia.render('auth/login', {})` → `inertia/pages/auth/login.vue`) via `resolvePageComponent` in `inertia/app.ts` (client) and `inertia/ssr.ts` (SSR entry, currently disabled — see `config/inertia.ts` `ssr.enabled`). Both wrap pages in `inertia/layouts/default.vue`.
- The `~/` alias points at `inertia/`, and `@generated` points at `.adonisjs/client/` (see `vite.config.ts`).
- `inertia/client.ts` sets up a Tuyau client (`createTuyau`) from the generated registry, giving typed, autocompleted access to server routes/controllers from Vue components (`import { client } from '~/client'`).
- Styling is Tailwind v4 (via `@tailwindcss/vite`) plus DaisyUI.

### Auth

Session-based auth only (`config/auth.ts`, guard `web`, no remember-me tokens). `User` (`app/models/user.ts`) composes the generated `UserSchema` with `withAuthFinder` for credential verification. Guest-only and auth-only route groups are declared per-group in `start/routes.ts` using `.use(middleware.guest())` / `.use(middleware.auth())`; `silent_auth_middleware` runs globally so `auth.user` / `inertia_middleware`'s shared `user` prop are populated (or `undefined`) on every request regardless of the route's guard.
